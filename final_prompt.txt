User: Performance Optimization Task – Immutable Baseline Under Concurrency

You are a senior backend engineer working on a latency‑sensitive service. A small Python service already exists and behaves correctly, but its tail latency and throughput under concurrent load are not good enough. Your job is to design an optimized solution **without touching the baseline files** and to demonstrate the improvement in a repeatable way.

This is a **performance optimization** task, not a feature change. Treat the current behavior as the spec: for the workload driven by `runner.py`, the optimized version must produce the same logical outputs and logs; only speed and efficiency may change.

---
## 1. Baseline (Read‑Only)

The repository starts with exactly two Python files:

* `baseline_worker.py` – processes jobs and appends structured JSON lines to a log file.
* `runner.py` – generates a fixed workload, runs a chosen worker module under concurrency, and reports latency/throughput.

Both files are **immutable** for this task. You may read them to understand the behavior, but you must not edit them. The load model in `runner.py` (job counts, concurrency, warm‑up, metrics) is also fixed and must be reused as‑is for all measurements.

---
## 2. Problem

When you run the baseline worker via `runner.py`, you will see:

* High P95/P99 latency for individual jobs.
* Lower‑than‑desired throughput (jobs per second).
* A lot of time spent opening, writing, flushing, and syncing the log file under a global lock.

Your goal is to provide an alternative worker implementation that keeps the same externally visible behavior but significantly improves tail latency and throughput for the same workload.

---
## 3. Hard Constraints

* Do not modify `baseline_worker.py` or `runner.py`.
* Use only the Python standard library (no third‑party packages).
* For the workload generated by `runner.py`, the optimized path must:
  * Process the same set of jobs.
  * Produce logically equivalent results and log records.
* You may change *how* work is scheduled, batched, or flushed, but not *what* work is done.
* Do not cheat: do not reduce the number of jobs, remove disk writes entirely, intercept or fake timing, or change how `runner.py` measures performance.

Any speedup must come from genuine engineering improvements such as less I/O per job, fewer contended locks, or better use of concurrency.

---
## 4. What You Should Build

Implement your solution by **adding** code instead of editing the baseline:

* Create one or more new modules (for example `optimized_worker.py`) that expose a function compatible with the baseline interface, such as `handle_request(job_id, payload, log_path)`.
* Make it straightforward to run either the baseline worker or your optimized worker under `runner.py` so their metrics can be compared under the same load.

The prompt deliberately does not prescribe specific techniques. Valid approaches might include buffering writes, background flushers, batching, reducing lock scope, or other designs that respect the constraints while improving performance.

---
## 5. One‑Command Benchmark – `run_tests`

Add an executable script named `run_tests` at the repository root. It should be runnable as:

```bash
./run_tests
```

At minimum, `run_tests` must:

* Run the **baseline** implementation through `runner.py` and collect metrics.
* Run the **optimized** implementation through `runner.py` under the same workload.
* Print, for both runs, human‑readable metrics including throughput and latency percentiles (at least P50, P90, P95, P99, plus an average).
* Exit with a non‑zero status if any run fails or required artifacts are missing.

You may add simple checks (for example, comparing basic log counts) to increase confidence that the two implementations are doing the same work.

---
## 6. Reproducibility and Outputs

Make it clear how to reproduce your results on a clean machine with Python 3:

* Document in a short `README.md` how to set up a minimal environment (for example, using a venv) and how to run:
  * The baseline path.
  * The optimized path.
  * The unified `./run_tests` command.
* Summarize, in that README, the main bottlenecks you observed and the key ideas behind your optimization,用比较高层的语言，不需要写成操作手册。
* Include一个简短的小表或项目符号，展示你自己机器上测到的前后对比（吞吐和若干延迟分位数）。

In addition to console output, `./run_tests` must write a machine‑readable JSON file named `perf_report.json` at the repository root with, at minimum:

* Baseline metrics (latency percentiles, throughput, wall‑clock time).
* Optimized metrics using the same fields.
* Simple derived numbers such as speedup factors or differences.

The exact JSON shape is up to you; keep it small and obvious so that automated checkers can parse it.

---
## 7. How Your Solution Will Be Judged

Your submission will be evaluated on:

* **Correctness** – the optimized path preserves the observable behavior of the baseline for the given workload.
* **Performance** – tail latency and throughput are clearly improved.
* **Engineering quality** – the code is simple, readable, and maintainable.
* **Reproducibility** – `./run_tests` works reliably on a fresh environment.
* **Honesty of evidence** – metrics and reports are consistent with what the code actually does.

Assume this could run in production under strict latency SLOs. Do not weaken the workload or modify the baseline files; focus on making the same work execute faster and more efficiently.
