Role & Objective
You are a senior backend engineer working on a latency-sensitive Python service. Your objective is to design and implement an optimized worker implementation and benchmarking harness that improves tail latency and throughput under concurrent load, while strictly preserving the observable behavior and outputs of an existing baseline implementation.

Inputs & Context
- You are given a small Python repository that initially contains exactly two files:
  - baseline_worker.py: processes jobs and appends structured JSON lines to a log file.
  - runner.py: generates a fixed workload, runs a chosen worker module under concurrency, and reports latency/throughput.
- The workload model in runner.py (total requests, warm-up requests, concurrency level, logging paths, and metric calculations) is fixed and must be reused as-is for all measurements.
- The baseline behavior, as implemented by baseline_worker.py and invoked via runner.py, is the specification for correctness. The optimized implementation must produce logically equivalent results and logs for the workload driven by runner.py.
- The repository root is the current working directory. All new files you create must be placed in this directory.

Step-by-Step Instructions
1. Baseline Understanding (Read-Only)
   - Read baseline_worker.py to understand how jobs are processed, how logs are written (including data fields and JSON structure), and what deterministic computations are performed per request.
   - Read runner.py to understand how the workload is generated and executed: total number of requests, number of warm-up requests, concurrency level, log directory and file paths, and how latency metrics and throughput are computed and reported.
   - Do not modify baseline_worker.py or runner.py in any way.

2. Design an Optimized Worker
   - Design an alternative worker implementation in a new module (for example, optimized_worker.py) that exposes a function with the exact same interface as the baseline:
     - handle_request(job_id: int, payload: str, log_path: str) -> dict
   - Ensure that, for the same inputs, the optimized handle_request returns a deterministic dictionary that is logically equivalent to the baseline result (same key fields and values to the extent required by the spec).
   - Ensure that the optimized worker writes structured JSON log records that are logically equivalent to those produced by the baseline worker, for the same workload and log path.
   - Keep the same set of jobs: for the workload generated by runner.py, the optimized worker must process the same job IDs with the same payloads.

3. Performance Optimization Strategy
   - Identify the primary bottleneck in the baseline implementation: frequent opening of the log file, per-request write+flush+fsync operations, and serialization of log writes under a global lock.
   - Design and implement optimizations using only the Python standard library, such as (but not limited to):
     - Buffering or batching of log writes to reduce the number of file open/flush/fsync operations.
     - A background log flusher thread or worker that consumes queued log records and writes them to disk in batches.
     - Reduced lock contention by narrowing critical sections, using per-log-path writers, or using thread-safe queues instead of a single global lock.
     - Any other improvements that maintain the same logical outputs and durability semantics while reducing overhead.
   - Do not:
     - Reduce the number of jobs.
     - Remove log writes entirely or skip required fields.
     - Intercept, fake, or alter the timing measurements performed by runner.py.
     - Modify how runner.py measures performance or how many jobs it executes.

4. Implement the Optimized Worker Module
   - Create a new Python module, for example optimized_worker.py, in the repository root.
   - Implement handle_request(job_id, payload, log_path) so that:
     - It performs the same deterministic computation on the payload as baseline_worker.handle_request (e.g., character counts, vowel counts, or any other deterministic work used in the baseline), either by reusing baseline code or by re-implementing equivalent logic.
     - It constructs JSON log records with the same logical fields as the baseline (e.g., job_id, payload-related fields, derived metrics, timestamps).
     - It writes these log records to the same log_path that runner.py passes in, but with improved performance characteristics, for example by:
       - Enqueuing log lines into an in-memory buffer or thread-safe queue.
       - Having a dedicated background writer that periodically flushes buffered log lines to disk in batches and performs fsync less frequently while preserving durable writes.
       - Managing synchronization in a way that minimizes contention under the concurrency level defined in runner.py.
     - It remains thread-safe under the concurrency level specified in runner.py.

5. Make Runner Use Either Worker
   - Ensure your optimized module can be invoked by runner.py using the existing --worker argument mechanism:
     - When runner.py is run with --worker baseline_worker, it must use the baseline implementation and write to the baseline log file (as currently coded).
     - When runner.py is run with --worker optimized_worker (or your chosen module name), it must use your optimized worker and write to a separate optimized log file (as defined by runner.py).
   - Do not modify runner.py; instead, rely on the fact that it imports the specified worker module and calls handle_request(job_id, payload, log_path).

6. Implement One-Command Benchmark Script: run_tests
   - At the repository root, add an executable script named run_tests that can be invoked as:
     - ./run_tests
     - On platforms where ./run_tests is not directly executable, it should still be runnable with an explicit Python interpreter (for example, python run_tests).
   - In run_tests, implement the following behavior:
     - Run the baseline implementation via runner.py with the appropriate --worker flag and collect metrics:
       - Use runner.py without modifying its internal constants.
       - Capture its JSON output using the --output-json argument into a baseline metrics file (e.g., baseline_metrics.json).
     - Run the optimized implementation via runner.py with the same workload and collect metrics into an optimized metrics file (e.g., optimized_metrics.json).
     - Ensure that both runs complete successfully; if either fails, or if required artifacts such as metrics or logs are missing, run_tests must exit with a non-zero status code.
   - After both runs complete, implement basic correctness checks, such as:
     - Compare the number of log lines written by the baseline and optimized implementations to ensure they match the expected total (including both warm-up and measured requests) and match each other.
     - Optionally, parse corresponding log records and confirm that key deterministic fields (such as job_id, payload-derived fields, or other deterministic attributes) are identical between baseline and optimized logs for the same job IDs.
   - In run_tests, print human-readable metrics for both runs, including at minimum:
     - Throughput (requests per second).
     - Latency percentiles: P50, P90, P95, P99.
     - Average latency.
   - Ensure that all output metrics are based on the data returned by runner.py and that the workload configuration in runner.py is not altered.

7. Reproducibility and Reporting
   - Add a short README.md at the repository root that:
     - Briefly describes how to set up a minimal environment using Python 3 (for example, optionally using a virtual environment such as venv) without going into step-by-step manual instructions.
     - Explains how to run:
       - The baseline path via runner.py with the baseline worker.
       - The optimized path via runner.py with the optimized worker.
       - The unified run_tests command.
     - Summarizes, in high-level language, the main bottlenecks observed in the baseline (e.g., excessive per-request I/O and lock contention) and the key ideas behind your optimization (e.g., batching, background flushing, reduced lock scope).
     - Includes a brief table or bullet list with example performance numbers measured on your own machine, showing before/after comparisons for throughput and a few latency percentiles (at least the ones reported by runner.py).

8. Machine-Readable Performance Report
   - Modify or implement your run_tests script so that, in addition to console output, it writes a machine-readable JSON file named perf_report.json at the repository root.
   - The perf_report.json file must include at least:
     - Baseline metrics: latency percentiles (P50, P90, P95, P99, average), throughput (requests per second), and wall-clock time.
     - Optimized metrics with the same fields.
     - Simple derived values such as:
       - Throughput speedup factor (optimized throughput divided by baseline throughput).
       - Latency ratios or differences for the same percentiles.
   - Keep the JSON structure small, clear, and self-explanatory so that automated checkers can easily parse it.

9. Constraints & Preferences
   - Do not modify baseline_worker.py or runner.py.
   - Use only the Python standard library; do not introduce any third-party dependencies.
   - Do not change the number of jobs, the concurrency level, the warm-up behavior, or how runner.py measures performance.
   - Do not remove disk writes entirely, fake timing, or bypass the logging functionality.
   - Any speedup must come from genuine engineering improvements such as reducing per-request I/O, reducing lock contention, or improving concurrency behavior.
   - Ensure that the optimized worker maintains the same logical behavior and outputs as the baseline for the workload defined by runner.py.

10. Quality Gates
   - Consider the task complete only if all of the following are true:
     - The optimized worker can be invoked by runner.py using the --worker argument and runs successfully under the fixed workload.
     - For the same workload, baseline and optimized logs have matching job counts and logically equivalent records for corresponding job IDs.
     - The run_tests script executes both baseline and optimized benchmarks, prints human-readable metrics, and exits with a non-zero status on failure conditions (such as missing artifacts or mismatched basic log counts).
     - A perf_report.json file is generated at the repository root with both baseline and optimized metrics, plus derived comparisons.
     - The optimized implementation clearly improves tail latency (P95/P99) and throughput compared to the baseline for the provided workload, without violating any of the above constraints.

Critical Compliance Instructions
- Never modify baseline_worker.py or runner.py.
- Use only the Python standard library.
- Preserve the logical behavior and outputs of the baseline for the workload defined by runner.py.
- Do not alter the workload configuration, timing measurements, or metric calculations in runner.py.
- All performance improvements must come from real engineering optimizations (such as reduced I/O, less lock contention, or better concurrency), not from reducing work or faking measurements.
